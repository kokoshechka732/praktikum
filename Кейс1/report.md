# Кейс 1. Поиск нетипичного поведения заявок на закупку

Данные: `students1.csv` — 12 162 события, 1 000 заявок, 41 пользователь, 22 варианта маршрута, срез 01.07.2026 00:00 UTC+03:00.
Сдача: `anomalies.csv` (66 строк по 56 заявкам), этот отчёт, код `analysis.py`.

## 1. Инструменты и воспроизводимые шаги

Python 3.14, только стандартная библиотека (`csv`, `statistics`, `datetime`).

```
python analysis.py      # читает students1.csv, пишет anomalies.csv и таблицы в out/
```

1. Читаю журнал (UTF-8 с BOM), события внутри заявки сортирую по числовому `EventIndex`, а не по времени: в одну секунду попадает несколько событий. Проверил инварианты: 12 162 уникальных `EventId`, ровно один `process_started` на заявку, `EventIndex` идёт подряд, порядок совпадает с порядком времени (0 нарушений), отрицательных длительностей нет, `Amount` внутри заявки не меняется.
2. Длительность задания — пара `task_created` → `task_completed` по `TaskId`, а не по названию этапа: повторное выполнение создаёт новое задание. Шкалы две, календарные часы и рабочие по календарю организации (пн–пт, 09:00–18:00, без праздников и обеда).
3. Базовая линия по когортам `RequestType × ActivityName`: n, медиана, p90, p99, максимум, MAD (`out/baseline_durations.csv`), плюс фактические роли по этапам (`out/roles_by_activity.csv`).
4. Проверяю правила R1–R7: регламентные без порогов, статистические с порогом из когорты. Каждое проверяю вопросом «мог ли процесс законно закончиться так?», отброшенные правила с числами — `out/rejected_rules.csv` и раздел 5.
5. Собираю `anomalies.csv`: заголовки по шаблону, все `ProcessInstanceId` есть в журнале, дублей пар (заявка, тип) нет, строки по приоритету. `out/candidates.csv` — те же строки с номером правила.

## 2. Что считаю обычным поведением и на каких данных это основано

Маршрут успешной заявки по бизнес-описанию: проверка (specialist) → согласование руководителем (manager) → бюджет (finance) → [юрист для contract] → исполнение (procurement) → завершение. Возврат идёт через доработку заявителем и повторную проверку, отказ руководителя завершает заявку с `rejected`.

- Роли закреплены за этапами: на 7 этапах роль исполнителя совпадает с ожидаемой в 100 % случаев (специалист 1 181 закрытие, менеджер 1 141, финансист 941, закупщик 939, юрист 182, заявитель 173, аудитор 16). Исключение одно — 8 закрытий «Согласования руководителем» ролью `requester`. У всех 41 пользователя ровно одна роль, поэтому проверки разделения обязанностей получаются точными.
- Маршрут стабилен: 22 варианта, из них 62,9 % — прямой standard-путь `Регистрация → Проверка → Руководитель → Бюджет → Исполнение → Завершение`; 15,0 % — он же с юридической проверкой; 9,2 % — с одним циклом доработки; 4,5 % — отказ руководителя; 2,0 % — доработка плюс юрпроверка. Возвраты и отказы штатные: 173 `return` и 51 `reject`, все на этапе руководителя, в файл они не попадают.
- Суммы внутри типа стабильны (медиана 27–28 тыс., p99 135–175 тыс.), финансового порога в описании нет, поэтому суммы — контекст, а не критерий.

Длительности по когортам (календарные часы, медиана / p99 / максимум):

| Этап | standard | contract | urgent |
|---|---|---|---|
| Проверка заявки | 0,40 / 23,0 / 198 | 0,42 / 15,6 / 198 | 0,14 / 198 / 261 |
| Согласование руководителем | 2,11 / 66,0 / 68,9 | 1,98 / 66,2 / 66,5 | 0,70 / 16,0 / 16,3 |
| Согласование бюджета | 2,83 / 66,1 / 71,0 | 2,80 / 65,5 / 66,8 | 0,92 / 16,6 / 65,9 |
| Проверка договора | — | 17,28 / 72,6 / 76,0 | — |
| Исполнение заявки | 19,3 / 88,3 / 95,5 | 18,3 / 76,2 / 89,8 | 1,79 / 65,0 / 67,8 |

Отсюда два вывода для метода. Календарные часы включают ночи и выходные: 65,9 ч на бюджете — это пятница 17:22 → понедельник 11:16, то есть 0,6 рабочих часа. И p99 загрязнён самими аномалиями: восемь заданий по 198–261 ч — это 4 % когорты `urgent × Проверка`, её p99 равен 198 ч, такую аномалию по p99 не поймать. Поэтому основная шкала — рабочие часы, а порог — «медиана + 10·MAD». Полный цикл заявки: медиана 27,5 ч, p99 197,6 ч (8,2 дня), максимум 292,7 ч.

## 3. Критерии поиска и почему выбраны такие сравнения

Класс правила виден в самом `AnomalyType`: нарушения регламента порога не требуют, статистические отклонения требуют и всегда идут с числами когорты.

| № | Правило | Как проверяется | Класс | Приоритет |
|---|---|---|---|---|
| R1 | Пропуск обязательного этапа | для `fulfilled` нет «Согласования руководителем» | нарушение | 1 |
| R2 | Нарушен порядок этапов | «Исполнение» раньше «Согласования бюджета» (и юрпроверки) | нарушение | 1 |
| R3 | Этап выполнен не тем исполнителем | роль закрытия ≠ ожидаемая роль этапа | нарушение | 1 |
| R3b | Самосогласование | инициатор заявки сам закрыл этап руководителя | нарушение | 1 |
| R4 | Зависшее задание | рабочие часы > медиана когорты + 10·MAD и > 8 раб. ч | отклонение | 2 |
| R5 | Повторный этап без основания | две проверки подряд без возврата и доработки | отклонение | 3 |
| R6 | Зависшая заявка | открыта на срез дольше p99 цикла (8,2 дня) | отклонение | 3 |
| R7 | Внеплановая проверка аудитора | этап вне обязательного маршрута | наблюдение | 4 |

- Сравниваю внутри когорты `RequestType × Activity`: медиана проверки 0,14 ч у срочной и 0,40 ч у стандартной, юрпроверка 17,3 ч у договорной. Глобальный порог либо пропускал бы срочные, либо массово флагал договорные.
- Порог «медиана + 10·MAD», а не p99: p99 неустойчив к самой аномалии и к размеру когорты. Второе условие, «больше одного рабочего дня», защищает от выбросов на малых когортах.
- Правила ограничены по исходу: обязательные этапы проверяются только для `fulfilled`, отклонённая или отменённая заявка законно останавливается раньше. Так отсеклись 15 ложных срабатываний. Приоритеты 1 → 4 задают порядок строк в файле.

## 4. Результаты

Всего 66 строк по 56 заявкам — 5,6 % журнала.

| Тип отклонения | Заявок | Класс |
|---|---|---|
| Пропуск обязательного согласования | 16 | нарушение |
| Нарушен порядок этапов (исполнение раньше бюджета) | 8 | нарушение |
| Этап выполнен не тем исполнителем | 8 | нарушение |
| Самосогласование (нарушение четырёх глаз) | 2 | нарушение |
| Зависшее задание (60 рабочих часов на проверку) | 8 | отклонение |
| Повторное выполнение этапа без основания | 8 | отклонение |
| Зависшая заявка (открыта 139–161 день) | 8 | отклонение |
| Внеплановая проверка аудитора | 8 | наблюдение |

Показательные примеры (ID сокращены, полные в файле):

1. `10daf811…` (standard, 54 514 ₽) — исполнена с результатом `fulfilled`, но заданий руководителя в истории нет: `Проверка → Бюджет → Исполнение → Завершение`. В когорте standard руководитель участвует в 98,3 % исполненных заявок. Таких заявок 16, у 8 из них ещё и зависшая проверка.
2. `cea423f9…` (standard, 54 514 ₽) — «Исполнение заявки» закрыто 16.02 09:55, «Согласование бюджета» только 17.02 13:28: бюджет утверждён после исполнения. В трёх договорных заявках той же группы юрпроверка закрыта позже исполнения.
3. `65ba6ad5…` — «Согласование руководителем» закрыто пользователем с ролью `requester` вместо `manager`. Таких закрытий 8, в двух это сам инициатор заявки.
4. `692f3878…` (contract, 198 ч) — проверка заняла 60 рабочих часов (6,7 рабочего дня) против медианы 0,41 раб. ч при p99 когорты 1,3 раб. ч. Группа однородная: 7 заданий по 198 ч и одно на 261 ч, все стартуют в 09:00–09:10, то есть один сценарий «задание висит неделю», а не разброс.
5. `7f0d02c6…` — две проверки подряд (26.01 09:35 и 11:26, разные специалисты) без возврата и доработки: в остальных 992 заявках повторная проверка бывает только после доработки. `5bd32a9a…` — не завершена на срез 160 дней (старт 21.01–11.02), стоит на задании от 21.01 10:09, поэтому по его длительности известна только нижняя граница.

Проверку полноты сделал тремя обратными проходами. Скан всех 7 этапов без правил: задания дольше 24 рабочих часов есть только у «Проверки заявки» — 8 заданий (максимум 60 ч), у остальных 0 (максимумы 6,8 / 8,8 / 17,5 / 14,0 / 3,2 / 5,3). Пересечения групп: R1 ∩ R4 = 8 заявок (зависшая проверка и есть причина обхода руководителя), R3 ∩ R3b = 2, остальные группы не пересекаются, поэтому 66 строк дают 56 заявок. Структура: восемь классов по 8 заявок и группа из 16, которая по длительности проверки делится ровно на 8 + 8. За пределами файла остались кандидаты с недоказанным бизнес-смыслом: пауза 63 ч перед первым заданием (медиана 0,25 ч), 15 выбросов по сумме.

## 5. Ложные срабатывания, ограничения, незавершённые процессы, ручная проверка

| Отброшенное правило | Срабатываний | Осталось | Причина |
|---|---|---|---|
| Договорная заявка без юрпроверки | 15 | 0 | все 15 отклонены или возвращены до этапа юриста; юрпроверка обязательна только для исполненных |
| Открытая заявка как аномалия | 10 | 8 | открытая заявка не аномалия; оставлены открытые дольше p99 цикла |
| Аномальная сумма (3·IQR) | 15 | 0 | порогов в описании нет, выброс суммы не образует нарушения |
| События после среза | 25 в 10 заявках | 0 | дефект выгрузки, а не поведение процесса |
| Роль не соответствует этапу | 8 | 8 | расхождение только на «Согласовании руководителем» |
| Возвраты и отказы как аномалия | 224 | 0 | штатная ветка процесса |

- Длительность задания — ожидание в очереди плюс работа, по журналу их не разделить: «зависшее задание» может быть и ошибкой процесса, и паузой (отпуск, согласование вне системы).
- Нет назначения задачи на пользователя, поэтому проверить «закрыто не тем, кому назначено» нельзя, только соответствие роли этапу. Нет и истории изменения полей: R5 фиксирует факт повторного выполнения, а не изменение данных.
- 25 событий в 10 заявках имеют метку позже объявленного среза, хотя в описании сказано обратное: это дефект выгрузки, эти заявки не считались открытыми, их длительности в базовую линию не попали.
- Порог R4 откалиброван на 8 заданиях одной когорты; для когорт с малой дисперсией любое задание длиннее 8 рабочих часов попадёт в кандидаты. Это осознанно консервативно: цена — рост ручной проверки, а не пропуск аномалии.

Незавершённые заявки: на срез не завершены 10. Две открыты за 0,6 дня до среза — обычный рабочий процесс, в файл не попали. Восемь открыты 139–161 день и включены с пометкой про нижнюю границу длительности.

Ручная проверка: 8 из 1000 заявок с внеплановой проверкой аудитора (редкость нарушения не доказывает, нужно основание проверки); 6 из 8 закрытий «Согласования руководителем» ролью requester (не самосогласование, но и не согласование руководителем, возможно делегация — её признаков в журнале нет); 8 заявок с двумя проверками подряд, в 7 случаях разными специалистами, похоже на «вторую пару глаз», и если регламент это разрешает, R5 надо снять.

## 6. Использование AI

Языковую модель использовал для трёх вещей: предложить каталог проверок соответствия под это бизнес-описание, написать черновик кода правил и причесать формулировки объяснений. Каждая цифра пересчитана `analysis.py`, таблицы собраны из `out/*.csv`, каждое срабатывание я смотрел глазами по полной истории заявки (всего 56 заявок). Пять предложенных правил отброшены после проверки на данных: «договорная без юрпроверки» (15 ложных), «аномальная сумма» (15 срабатываний без бизнес-смысла), «открытая заявка = аномалия», «возвраты = аномалия», «события после среза = нарушение процесса» — все они в разделе 5. ID заявок, типы и числа модель не генерировала: файл собирается только скриптом из журнала.
